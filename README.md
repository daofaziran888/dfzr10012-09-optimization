# 实时流数据处理中心

面向实时数据处理团队的流式计算与管理中心。覆盖流数据源接入、流处理算子编排、窗口计算配置、状态后端管理、检查点恢复、反压监控、延迟追踪与流作业运维的完整实时计算链路。

这是一个前后端分离的管理平台：前端 React + Vite + TypeScript，后端 FastAPI（Python）。
两边各自独立启动，前端 dev server 已关掉自动打开页面，启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 React + Vite + TypeScript 前端
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/              统一请求封装
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false）
├── backend/                  FastAPI（Python） 后端
│   ├── app/routers/          每个业务模块一组接口
│   ├── app/services/         业务规则与状态流转
│   └── app/store.py          内存数据仓库与示例数据
├── .gitignore
└── docker-compose.yml
```

## 启动

### 后端

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
./run.sh
```

健康检查：`curl http://127.0.0.1:8000/api/health`

### 前端

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，
需要自己访问。`/api` 由 vite 代理到后端 `http://127.0.0.1:8000`。

## 约定

- 每个模块的前端页面在 `frontend/src/views/<模块>/index.vue`，后端接口在
  `backend/app/routers/<模块>.py`，业务规则在 `backend/app/services/<模块>.py`。
- 列表接口统一返回 `{ items, total, page, size }`，动作接口统一返回 `{ ok, message }`。
- 状态流转只允许在 `app/services` 里改，路由层不做业务判断。

## 窗口触发结果数据集

窗口计算配置除了维护窗口定义，还会产出一份可核对的**窗口触发结果数据集**。
相关规则集中在 `backend/app/services/window_engine.py`（归属算法）与
`backend/app/services/window_dataset.py`（版本、批次、检查点、消费侧口径）。

### 唯一归属规则

同一记录编号只能进入一个窗口，按以下顺序判定：

1. 事件只进入包含其事件时间、且窗口结束时间不晚于水位线（已闭合）的窗口实例；
2. 到达时间必须落在「窗口结束 + 延迟容忍」之内（含边界）；
3. 多个候选窗口同时可接纳时，取结束时间最早的那个。

因此延迟容忍从 15 放宽到 30 时，迟到事件会从较晚的窗口迁移到最早的可用窗口，
而不是同时进入两个窗口。

### 阈值调整与重算

`POST /api/window/{id}/threshold/preview` 只做预演，给出受影响事件与窗口；
`POST /api/window/{id}/threshold/actions` 才写入：

- 用同一批窗口事件分别按旧阈值、新阈值计算归属，**只有归属变化的窗口才重算**；
- 未变化的窗口从上一份完整批次里整行沿用，来源标记为「沿用快照」并保留原阈值版本；
- 每行都带 `窗口开始`、`窗口结束`、`窗口长度`、`滑动步长`、`延迟容忍`、
  `触发策略`、`阈值版本`、`来源`，可直接核对；
- 校验项覆盖窗口类型、触发策略、窗口边界对齐、阈值版本可追溯、同一记录编号只进入
  一个窗口、受影响事件均有归属；不通过则不发布。

### 版本与并发

- `window_version` 记录每个窗口的阈值版本历史（如 `v1 -> v2`）；
- `window_dataset` 中同一窗口最多一个「生效」批次，旧批次转为「历史」；
- 同一窗口的重算串行执行；相同幂等键或相同目标参数的并发请求只落成一个批次，
  所有调用方拿到同一个 `批次编号`；基线批次已过期时明确拒绝；
- 重算失败时上一份完整批次保持「生效」，任务流水记「失败」并留原因；
- `POST /api/window/{id}/repair` 顺着当前取数链路改正异常版本：只重建标注异常的
  行，其余行沿用历史快照，并收敛同时处于「生效」的重复来源。

### 检查点与消费侧

- `GET /api/checkpoint/{id}/restore` 只读取检查点声明的阈值版本对应的唯一批次；
  版本不一致、来源不唯一或存在重复归集时返回 409，不做跨版本合并；
- `POST /api/latency/{id}/sync` 是另一个业务入口，按 `事件记录编号` 到当前生效批次
  里关联窗口；命中多个窗口或批次不一致时拒绝写入；
- `GET /api/latency/sync` 批量巡检，`GET /api/checkpoint/version/consistency`
  给出检查点与消费侧的版本一致性总览。

### 升级流程

`GET /api/window/upgrade/plan` 列出现状，`POST /api/window/upgrade/actions`
以 `{"values": {"stage": "旧数据库"}}` 执行某一阶段：

| 阶段 | 作用 |
| --- | --- |
| 旧数据库 | 为缺少阈值版本与窗口边界的旧批次补齐字段后迁移 |
| 新环境 | 补齐阈值版本与基线数据集，重复执行不会产生第二份生效批次 |
| 部署回滚 | 把最近的阈值调整批次回退到上一份完整批次，并同步窗口定义版本 |
| 依赖兼容 | 校验检查点与消费侧都能解析到唯一阈值版本的数据集 |

### 验收样例

`WIND-0002` 为 60 秒滑动窗口、步长 30 秒、延迟容忍 15 秒。把延迟容忍改成 30 秒后：

- 只重算归属变化的 3 个窗口（30–90、60–120、90–150），其余窗口沿用快照；
- 迟到事件 `EVT-2001` 从 60–120 迁移到 30–90，`EVT-2003` 从 90–150 迁移到 60–120；
- `WIND-0003` 的版本、参数与生效批次完全不变。
